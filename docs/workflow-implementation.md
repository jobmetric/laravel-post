# Versioned post workflows

The package stores one workflow definition per post type. A saved definition is a draft until `PostWorkflowDefinitions::activate()` receives a fresh impact fingerprint and a complete status mapping. The impact preview reports affected streams, live versions, and open schedules for each current stage. The owning application must obtain explicit administrator confirmation. Activation preserves approvals, schedules, transition history and live revisions; it does not run transition tasks for migrated streams.

Each post has independent publication streams per locale. The reserved `*` stream contains shared public fields and has its own approve/apply path; it is excluded from language-stage mappings and does not run title/content validation. `PostLifecycle` stores immutable revisions, version-bound approvals, scheduled actions and audit events. The legacy `posts.status` and `posts.published_at` columns remain for compatibility; applications must use stream status and live revision IDs once a type has an active advanced definition.

## Owning application contract

The package does not authorize HTTP requests. The application must authorize the type and operation, verify the owner's edit lease where enabled, and submit the exact stream version and revision ID. Persist owner fields, translated editor documents and publication projections in one transaction. Acquire locks in this order: type workflow row, post row, stream row, schedule row. `PostLifecycle::published()` is the public read boundary; never render mutable post translations or drafts as live content.

`PostTypeRegistry::register('letter')->scheduledEditPolicy(ScheduledEditPolicy::Pause)` pauses pending schedules after a real draft change. Approval of the new draft does not resume the schedule: a manager must explicitly resume it with a new future due time. The default `Preserve` policy keeps the old approved version scheduled while later edits remain drafts. An unchanged save creates no new revision and does not pause a schedule.

`fieldOwnership()` declares whether public owner fields are `shared` or `internal`. Paths may be `slug`, `comment_status`, `metadata.key`, `media.collection`, or `taxonomies.collection`; group wildcards such as `metadata.*` are supported. Fields are shared by default. `internalMetadata()` remains a shorthand for private metadata keys and takes precedence over broad shared rules. The owner adapter must project only fields whose `getFieldOwner()` returns `shared`; translated fields are projected per language. Passwords, credentials, internal notes and unrelated application models must never enter revision payloads.

## Flow tasks and extensions

Graphs are validated by `WorkflowGraph`: one start state, unique IDs/statuses/slugs, no dangling transitions, and registered task configurations only. Saving a definition draft permits an unreachable stage so an unfinished diagram survives a reload; preview and activation of an enabled workflow require every stage to be reachable. Each stage has an immutable internal `status` key and an optional `content_status` applied to the language stream on entry. The live revision changes only on publication. Start position, start target port, state positions, and transition anchor ports are retained in the definition graph. Drivers implement `WorkflowTaskConfiguration` and a laravel-flow task contract for `PostPublicationStream`. Register trusted drivers in the Flow task registry before graph validation. The built-in drivers are `RequireContent`, `RequireExcerpt`, `RequireApprovedRevision`, `RequirePermission`, and `RecordTransition`; tasks receive the immutable revision payload during a transition. A direct `approve()` call on an advanced language stream requires a review-eligible state reached through a recorded transition for that exact revision and active definition.

Scheduled actions use `ScheduledPostActionRegistry`. The built-in `publish` handler makes the approved revision live. An application may register a trusted `ScheduledPostAction` with a unique key and pass that key as the final argument to `PostLifecycle::schedule()`. The handler receives the exact approved revision under the owner/stream/schedule transaction; retries of a completed schedule do not call it again. A failed transaction may retry the handler, so it must persist only transactional effects, such as an outbox row keyed by `execution_key`. External side effects such as sending a letter need a separate durable outbox worker and idempotent delivery; the key alone cannot guarantee exactly-once delivery. Resuming a paused schedule cannot switch its action key.

## Compatibility and rollout

Run the additive migration, backfill existing published content with an application-owned backup and dry-run command, then move reads/filters to publication streams. Do not drop the legacy columns until compatibility has been measured. Existing legacy Flow definitions may remain bound to old posts; new advanced definitions use separate stream-bound flows. The package has no Jobic or Editor.js dependency.
